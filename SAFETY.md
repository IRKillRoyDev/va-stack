# Safety

- **PII gate.** Do not read record files, vault page text, PDF bytes, or `raw_sentence`. Read only sterilized sentences, stored diagnosis sentences, and Missing Diagnosis text the program already wrote. Do not paste record text into chat, commits, issues, or pull requests. Names without a label are not redacted. If a sentence still shows a name, stop and ask the user to remove it before anything is sent.
- **Not legal or medical advice.** This project produces organized research notes only. It does not decide entitlement or diagnose anything. Any rating estimate is unofficial and always carries this notice: Unofficial estimate, not a VA decision. It is likely to differ after the VA exam (C&P exam). Confirm with a VA-accredited representative. Gap analysis never suggests worsening a condition or seeking care for the sake of a rating.
- **Verify with an accredited professional.** Before acting on any output, review it with a VA-accredited representative, a Veterans Service Organization (VSO), or a VA-accredited attorney or claims agent. Accreditation can be checked at https://www.va.gov/ogc/apps/accreditation/.
- **No filing.** The bot never submits, files, signs, or transmits a claim, form, or document to VA or anyone else. The user decides what, if anything, to file.
- **Where records go.** Record files are stored only in the folder the user chooses. The skills never commit, upload, or copy those files anywhere else. However, the text the bot reads from them is processed by the AI service the bot runs on, so it does leave the machine. Check that service's privacy terms before using real records. A fully offline setup needs a local model. To limit what is sent, the local-search skill runs `scripts/local_search.py` on the user's computer (no network calls, nothing written to disk) and returns capped, redacted snippets; the user approves the snippet list before any of it goes to the AI service, and whole pages are read only with explicit approval. Redaction is pattern-based and can miss things. Names are redacted only when labeled ("Name:", "Patient:", "Veteran:", or Mr./Mrs./Ms./Dr. followed by one or two capitalized words). Labels are matched in any case and include Name, Patient, Pt, Veteran, Claimant, Spouse, Dependent, Beneficiary, Examiner, Provider and Signed, plus compound labels such as "Patient's name", "Name of veteran" and "Last name", with the name after a colon, dash, fullwidth colon, "=", ".", "|", "is", line break or space; letters are matched as Unicode letters (accented names included), and middle initials, particles (de, la, van, von, del, da, St.), Jr./Sr. and Mc/Mac/O'/hyphenated names are taken in full. A negation or common word right after a label ("Not", "denies") is never taken as a name, and a capitalized surname after it is still redacted. Names are also redacted in typed corrections and in the exported report. Names without a label are not redacted (a known limit), including third-party names; the review's step (c), names we missed, is the backstop, and every review screen says "Check for names we didn't hide." So treat the report as containing PII and review each snippet before approving it. Redaction is pattern-based and can miss things in both directions: it can miss identifiers and it can over-redact ordinary numbers or dates. A bare year (for example "born in 1961") is not redacted.
- **Encrypted records vault (optional).** `scripts/records_vault.py` keeps records in a SQLCipher database on the user's computer, keyed with Argon2id from the user's password; the salt and Argon2id settings are stored unencrypted next to it in `<db>.kdf.json`. Every unlock shows a consent-to-share notice first and the password field stays disabled until the user consents; consent is never remembered. The password is typed locally and is never accepted as an argument or environment variable, printed, or logged. Every request must carry the requesting bot id, and an access log inside the encrypted file records the session, consent version, bot id, records searched, and each snippet sent (file, page, line, and a keyed HMAC-SHA256 of the text, never the text; a plain hash would let someone confirm a guessed snippet), plus each log read and verify. Log entries are HMAC-chained with a key derived (HKDF) from the vault key, and a MAC'd head (entry count and last MAC) is kept next to the database in `<db>.loghead.json`, so someone without the password who edits, deletes, truncates, or rolls back the database is detected by verify. Limits, stated plainly: anyone with the password can rewrite the whole access log and its head, so the log proves nothing against someone who knows the password. Rolling back the database and the head file together is only caught if you keep a copy of the head elsewhere: `Vault.export_head(path)` writes the signed head to a file you choose (keep it on other media), and `Vault.verify_log(external_head=path)` fails if the current log no longer contains that head. The KDF header (`<db>.kdf.json`: salt, Argon2id settings, registered bot ids) stays readable so the key can be derived, but it carries an HMAC keyed from the vault key (HKDF); after the key is derived the vault refuses to open if the header was edited or is unsigned, and it refuses Argon2id settings below the minimum before deriving. Bot ids are normalized and checked (and limited to a registered list when the vault has one), but an id is a claim, not a credential: any program on this computer can claim a registered id. Consent and the password are accepted only from the Unlock window or a real terminal (piped stdin is refused); code running inside the same Python process can always bypass an in-process consent check, so do not run untrusted code alongside the vault. New vaults refuse Argon2id settings below t=2, m=19456 KiB, p=1, one of the minimums in the OWASP Password Storage Cheat Sheet ("m=19456 (19 MiB), t=2, p=1", https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html, checked 2026-10-16); the default is RFC 9106's "SECOND RECOMMENDED option" ("Argon2id with t=3 iterations, p=4 lanes, m=2^(16) (64 MiB of RAM)", https://www.rfc-editor.org/rfc/rfc9106.txt, checked 2026-10-16). The SQLCipher driver only accepts the key as text, so opening the vault makes an immutable hex copy of the key that cannot be wiped. At the end of a session the key buffer and password buffer are overwritten with zeros and the database is closed. Python cannot fully guarantee memory wiping: the password from the prompt and decrypted record text exist as immutable Python strings that cannot be overwritten, the garbage collector and libraries may keep copies, and the operating system may write memory to swap or crash dumps. Use full-disk encryption and close the program when done.
- **Your review is the final check.** The report asks the user to open each record page at its vault link (every row and every flag points to the page, line and date) and answer Yes or No for each row: (a) confirm or correct what each quote means, especially flagged rows; (b) list anything in the file that is missing from the report; (c) list any names or personal details that redaction missed. On No, the user is asked to type the rest of the missing sentence or paragraph from the record, leaving out PII; the text is still run through redaction, the user is warned if anything was caught, and it is saved in the encrypted vault next to the row with the USER_UPDATED flag, the time, and an access-log entry (keyed HMAC only, never the text). The review works like a store checkout (`scripts/review_session.py`, shown in the `scripts/vault_ui.py` window or as a text walk-through): one row per screen with a progress count ("3 of 12"), the plain reading, the quote with its context, the vault pointer and any flags; big Yes and No buttons (y is Yes, n is No, Esc goes back, Right goes next; Enter alone is not a Yes, in the window or the text walk-through); Back and Next always available; then a summary listing every row as confirmed or user updated, with an Edit link back to each row, and one Confirm all button, which saves only after the user types back a short random phrase shown on the summary (a different phrase each session), so a pasted or repeated key stream cannot confirm on its own. Answers stay in memory until Confirm all; nothing is written to the vault before that, and Confirm all saves everything in one step with its log entries. Nothing is sent over the network. The original quote and the tool's reading are kept, never overwritten. Every row starts unreviewed; a row is final only after Yes, or after No with the user's text saved. The 21-526EZ column that explains how the disability relates to service is filled only from a Yes (the cited quotes) or that saved text, never by the tool on its own. In short, the user's review is the final check.
- **Quote checks and review writes.** The vault checks a quote against the unredacted record only inside the report builder, only for the whole cited sentence(s) and quotes of at least 20 characters, at most 50 times per unlock (then it fails closed until the next unlock), and it gives the same answer for a missing page as for a miss; there is no public quote-check call. A quote whose span carries a [REDACTED-*] tag (an SSN, date, name or other hidden value) is compared only after redaction, against the redacted record: the reader only ever sees the tag, so that is all the check confirms, and it blocks guessing at hidden values (a right and a wrong SSN get the same answer). Quotes with no tag are still compared against the unredacted text. Review answers are written only by Confirm all, which needs a single-use token from the review session, runs in one explicit transaction (the log head is written only after commit), and accepts only row ids from the current report. A row id includes a hash of the cited quotes and their pointers, so if the evidence changes, earlier answers no longer apply and the row is unreviewed again. These are in-process checks: as stated above, code running inside the same Python process can always bypass them.
- **What a cited quote means.** In short: the person reading checks what the quote means, and the tool only proves the quote is really in the record. Every cited quote is shown with its context (2 sentences before and 2 after, redacted) with the cited sentences marked `[QUOTE]...[/QUOTE]`. A partial quote is widened to the whole sentence(s) it sits in. If any negation or hedge word (for example not, cannot, n't, ruled out, unlikely, less likely than not, insufficient, inconsistent, doubtful, less than 50 percent) appears anywhere in that window, the row is flagged "Possible negative or qualified opinion; read the context." Rows are never dropped, and no row is labeled as backing a claim: every row is labeled "cited, needs your read."
- **Primary sources only.** Every legal statement cites its primary source, fetched in the same session with an "as of" date: 38 CFR (eCFR API), the U.S. Code (govinfo), DoD instructions (official DoD issuances site), or live VA.gov pages. Nothing is cited from memory. If a fetch fails, the bot stops.
- **No guessing.** If evidence is missing or ambiguous, the bot says so and lists it as a gap.
- **Crisis support.** If you are a veteran in crisis, or worried about one, contact the Veterans Crisis Line: dial 988, then press 1 (or text 838255, or chat online). Sources, checked 2026-10-16: https://www.veteranscrisisline.net/ and https://www.va.gov/health-care/health-needs-conditions/mental-health/. If you are in immediate danger, call 911.
- **No real patient data in this repo.** Everything under `tests/` is fictional.
